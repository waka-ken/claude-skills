# 必須対応メール → Notion タスク化 提案書

## 1. 課題

AWS や各種 SaaS から届く **必須対応メール**（請求・セキュリティ・規約更新・証明書期限・サポート期限など）が後回しになり、失念する。

### ゴール

1. メールを自動で読み取る  
2. **対応が必要か**を判定する  
3. 必要なものだけ **Notion のオールタスク** に落とす  
4. 可能な範囲で **具体対応**まで進める（ただし危険な自動操作はしない）

---

## 2. 結論（現実的な落としどころ）

### 設計方針の転換（重要）

**送信元・件名・サービスを人手で登録していく方式は採らない。**  
AWS の Require 対応メールも、他 SaaS の必須メールも、パターンを事前に列挙して保存する運用は続かない。

代わりに:

| やること | やらないこと |
|----------|--------------|
| **受信箱（または未読）を広く拾う** | サービスごとの allowlist をメンテする |
| **AI が「要対応か」を毎回判定** | 「この件名を監視」を1件ずつ登録する |
| **人が「これは無視」と一度教える** | 正しい必須メールのテンプレを蓄積する |
| 無視判定はシステムが **自動で学習・再利用** | 新サービス追加のたびに設定画面を開く |

人が最初に決めるのは実質これだけ。

1. **どの Gmail を監視するか**（GAS が動く Google アカウント＝その受信箱）  
2. **フィードバックの置き場**（Slack のリアクション or Notion のステータス）

サービス追加・新種の AWS メールが来ても、登録作業は発生しない。

### フェーズ概要

| 段階 | やること | 自動化の度合い | 推奨 |
|------|----------|----------------|------|
| **Phase 0** | 監視対象 Gmail を1つ決める（フィルタの細かい整備は不要） | 設定1回 | 必須 |
| **Phase 1** | 未読を広く取得（**15分**ポーリング）→ AI 判定 → Notion + Slack | ほぼ全自動 | **ここから着手** |
| **Phase 1.5** | （任意）Gmail `users.watch` + Pub/Sub で新着駆動に切替。判定ロジックは共通 | 即時寄り | 遅延要件があるときだけ |
| **Phase 2** | 「無視」フィードバックで denylist 自動成長、重複排除 | 全自動 | Phase 1 安定後 |
| **Phase 3** | 「手順付きドラフト対応」まで（コンソール操作は人が実行） | 半自動 | 価値が高い |
| **Phase 4** | API/CLI で安全な対応のみ自動実行 | 限定自動 | 慎重に・対象を絞る |

**「メールを読んで、AWS コンソール操作まで勝手に完了」は現実的ではない。**  
理由は、認証（MFA）、アカウント権限、誤操作コスト、メール文面だけでは不足するコンテキストが多いため。

現実的な完成形は次のとおり。

```
メール到着（どのサービスでも可・事前登録なし）
  → GAS が未読を広く取得
  → 既知の「無視ルール」に当たればスキップ（学習済みのみ）
  → Gemini が「要対応 / 無視可 / 要確認」判定
  → 要対応だけ Notion タスク化 + Slack 通知
  → 人が対応 / または「これは無視でよい」とフィードバック
  → 無視フィードバックは次回から同種を自動スキップ
```

既存の **朝タスク通知**・**日次レポート**・**Notion × Claude 開発パイプライン** はそのまま活かし、本機能は「入力源の追加」として接続する。

## 3. 前提・制約

| 項目 | 内容 |
|------|------|
| メール置き場 | **GAS が紐づく Gmail**（追加のメール種別登録は不要） |
| 判定 AI | 既存どおり **Gemini**（GAS から直接呼べる） |
| タスク先 | 既存 `[DB]オールタスク管理` |
| 通知 | 既存 Slack DM（`common.gs` の `notifySlack_`） |
| Claude 開発パイプライン | **コード変更が必要な対応**だけ `AIステータス=AIに依頼` に繋げる。請求・MFA・アカウント確認には使わない |

### トリガー方式: 「定期監視しかできないのか？」

**結論: Gemini 単体では新着メールを検知できない。**  
Gemini は「届いたメールの中身を判定する脳」であり、Gmail の着信イベントを購読する機能はない（Gmail 画面上の Gemini も、今回のようなバックグラウンド自動化のトリガーには使えない）。

新着で動かすなら、**Gmail 側の仕組み**が必要になる。

| 方式 | 遅延 | 既存スタックとの相性 | 複雑さ | 本提案での位置づけ |
|------|------|----------------------|--------|-------------------|
| **A. GAS 時間トリガー（ポーリング）** | 1〜15分 | 既存朝タスク/日次と同一 | 低 | **Phase 1 推奨** |
| **B. Gmail API `users.watch` + Pub/Sub プッシュ** | ほぼ即時（数秒〜数十秒） | GCP プロジェクト・OAuth・エンドポイントが追加で必要 | 高 | Phase 1.5 以降のオプション |
| C. Zapier / Make 等の「New Email」 | ほぼ即時〜数分 | 外部 SaaS 依存・月額 | 中 | 急ぎの暫定なら可 |

```
誤解されやすい分担:

  [新着検知] ← Gmail / Pub/Sub / GASタイマー の仕事（Gemini ではない）
       ↓
  [要対応判定] ← Gemini の仕事
       ↓
  [Notion / Slack] ← 既存連携
```

#### 方式 A（推奨スタート）: 短い間隔のポーリング

GAS に「新着メール onReceive」トリガーは無い。代わりに 1〜5 分間隔で未読を見る。

- 必須対応メール（請求・期限）の用途では、**数分遅れは実務上ほぼ問題にならない**
- 追加インフラゼロ、既存 `common.gs` と同じ運用
- 失敗時も次のポーリングで拾える（プッシュより復旧が単純）

#### 方式 B（新着駆動）: Gmail Push

公式手順は次のとおり（[Gmail push notifications](https://developers.google.com/workspace/gmail/api/guides/push)）。

```
新着 / メールボックス変更
  → Gmail が Cloud Pub/Sub へ通知（中身は historyId のみ）
  → Pub/Sub が HTTPS エンドポイントへ push
  → 受信側が history.list で差分取得
  → （ここで）Gemini 判定 → Notion / Slack
```

注意点:

- `users.watch` は **最大7日で期限切れ** → 毎日更新ジョブが必須
- 通知は「新着本文」ではなく **変更があったこと** だけ。本文取得は別 API
- GCP（Pub/Sub）、OAuth 同意画面、公開 HTTPS（Cloud Functions / Cloud Run / GAS Web App 等）が必要
- GAS だけで完結しにくく、**いまのリポジトリ構成より一段重い**

#### 推奨判断

| 要件 | 選ぶ方式 |
|------|----------|
| 忘れ防止・タスク化が主目的 | **A（1〜5分ポーリング）で十分** |
| 「届いたら数十秒以内に Slack」が必須 | B を Phase 1.5 で追加 |
| まず動かして学習ループを回したい | **必ず A から**（B は後付け可能。判定ロジックは共通化できる） |

「Gemini なら新着で動かせるのでは？」への短答: **動かせない。動かすのは Gmail Push かタイマー。Gemini はその後段。**

### メール取得・判定の置き場

| 方式 | メリット | デメリット | 推奨 |
|------|----------|------------|------|
| **Gmail + GAS（GmailApp）・未読スキャン** | 登録ゼロで始められる | 初期はノイズ学習が必要。トリガーはポーリング | **Phase 1** |
| Gmail API Push + Gemini | ほぼリアルタイム | GCP / watch 更新 / エンドポイント運用 | 必要なら後付け |
| ドメイン allowlist で先に絞る | 誤検知が減る | サービス追加のたびに登録 | 非推奨 |
| 各サービスの Webhook | 正確 | サービスごとに実装 | 将来の補完のみ |

## 4. 「登録しない」取得・判定モデル

### 4.1 何を人が登録しないか

次は **メンテ対象にしない**（提案書の旧案からの明確な撤回）。

- AWS Require / Action required の件名一覧  
- サービスごとの From ドメイン allowlist  
- 「このメールは保存しておけ」的なサンプルメール登録  
- 新サービスのたびに設定を足す作業  

### 4.2 代わりに何で絞るか（3層）

```
① 機械的な粗い除外（固定・ほぼメンテ不要）
    例: カテゴリ Promotions / Social、自分宛の送信済み、既読済み
         ↓
② 学習済み denylist（人が一度「無視」したものだけ自動蓄積）
    例: newsletter@example.com、件名に含まれる定型フレーズ
         ↓
③ Gemini が文面から判定（本命）
    「放置すると金銭・セキュリティ・アカウント継続に影響するか」
```

①は Gmail の標準カテゴリや `is:unread` 程度で足りる。  
②は **正しい必須メールを登録するのではなく、ノイズ側だけ覚える**ので負担が小さい。  
③が本体なので、未知の AWS メールや初めての SaaS でも拾える。

### 4.3 取得クエリ（登録なしの例）

```
is:unread -category:promotions -category:social -label:email-ingestor/done
```

必要なら後から「仕事用ラベルだけ」などに狭められるが、**初期はこれで十分**。  
「どのサービスか」は AI が From / 本文から推定し、Notion の `サービス` に書く（人が事前定義しない）。

### 4.4 判定カテゴリ（Gemini 出力）

| カテゴリ | 意味 | Notion | Slack |
|----------|------|--------|-------|
| `action_required` | 放置すると課金停止・ロック・期限切れ等のリスク | **タスク作成** | 即通知 |
| `review` | 内容確認は必要だが緊急ではない | タスク作成（優先度低） | まとめ通知でも可 |
| `fyi` | 情報のみ | 作成しない | なし |
| `ignore` | マーケ・ニュースレター等 | 作成しない | なし |
| `uncertain` | AI が自信なし | タスク作成（要確認タグ） | 通知 |

### 4.5 フィードバックで「登録代わり」にする

人がやる追加作業は、誤ってタスク化されたときだけ。

| 操作（例） | システムの学習内容 |
|------------|-------------------|
| Slack で 👎 / 「無視」リアクション | From ドメイン or From アドレスを denylist に追加 |
| Notion でタグを「対象外」にする | 同上 + 件名パターン（任意） |
| 「これは必須だった」と修正 | 取りこぼしログをプロンプト改善に使う（稀） |

ポイント: **必須メールのホワイトリストを育てない。無視リストだけが育つ。**  
新種の必須メールは毎回 AI が拾うので、取りこぼし対策の登録作業が要らない。

### 4.6 自動対応してはいけないもの（明示）

以下は **必ず人が確認**する。自動クリック・自動ログイン・自動承認はしない。

- MFA / ログイン確認リンク
- 支払い方法変更・高額課金の確定
- IAM / ルートアカウント関連
- 「アカウントが侵害された」系のフィッシング疑いメール
- 「今すぐクリック」だけの誘導（公式コンソール URL が本文に無いもの）

フィッシング対策として、タスク本文には **メール内の生リンクをそのまま「押せ」と書かない**。  
代わりに「AWS コンソールの Billing / Support を開いて確認」と手順化する。

## 5. 全体アーキテクチャ（Phase 1）

```
[ あらゆるサービスからのメール ]
     │  ※ From / 件名の事前登録なし
     ▼
[ Gmail 受信箱（GAS 実行アカウント） ]
     │
     ▼  5〜15分ポーリング
[ Google Apps Script: email_alert_ingestor.gs（新規） ]
     │  ① is:unread を広く取得（Promotions/Social は除外）
     │  ② 学習済み denylist に当たれば既読化してスキップ
     │  ③ Gemini で分類・要約・対応手順生成
     │  ④ 重複チェック（Message-ID）
     │  ⑤ 要対応のみ Notion オールタスクへ作成
     │  ⑥ Slack DM 通知（👎 で「今後無視」を学習）
     │  ⑦ 処理済ラベル付与 + 既読化
     ▼
[ Notion オールタスク ]
  ・タグ: 未着手
  ・ソース: メール
  ・サービス: AI 推定（事前マスタ不要）
  ・本文: 背景 / やること / 完了条件
     │
     ▼（既存）
[ 朝タスク通知 / 日次レポート ]
```

既存ファイルとの関係:

| 既存 | 役割 |
|------|------|
| `common.gs` | Notion / Slack ヘルパー流用 |
| `morning_tasks.gs` | 翌朝に必須メール由来タスクもまとめて通知 |
| `notion_task_extractor.gs` | 日次整理に乗る（特別な変更は最小） |
| `github_dispatch.gs` | **原則接続しない**（インフラメール ≠ コード実装） |

## 6. Notion データ設計（提案）

オールタスク DB に、メール由来を識別するプロパティを足す。

| プロパティ | 型 | 用途 |
|------------|-----|------|
| `ソース` | select | `メール` / `議事録` / `手動` など |
| `サービス` | select または text | AI が推定（未知サービスは「その他」で可。マスタ先登録不要） |
| `緊急度` | select | `緊急` / `通常` / `低` |
| `期限` | date | メールから抽出（あれば） |
| `メールMessage-ID` | text | 重複防止のキー |
| `元メール件名` | text | 追跡用 |
| `対応方針` | select | `人対応` / `対象外（学習用）` / `AI開発依頼可` |

`対応方針=対象外` にしたタスクは、次回以降の denylist 学習に使う。

### タスク本文テンプレート（自動生成）

```markdown
## 背景
- サービス: （AI推定）
- 件名: ...
- 受信日時: ...
- 要約: ...

## やること
1. 公式コンソール（ブックマークから）を開く
2. ...
3. 完了したら Notion のタグを「完了」にする

## 完了条件
- [ ] 請求/セキュリティ上のブロック要因が解消している
- [ ] 同様の再送メールが止まっている（またはステータス確認済み）

## 参考
- ※メール内リンクはフィッシングの可能性があるため、ブックマークからコンソールへ入ること
```

## 7. Phase 別の実装計画

### Phase 0（数十分）— 監視アカウントを決めるだけ

1. GAS を動かしている Google アカウントの Gmail を監視対象にする  
2. 必須通知が別アドレスに来ている場合のみ、そのアドレスへ転送（**サービス種別の登録ではない**）  
3. 細かい Gmail フィルタやラベル分けは **作らなくてよい**

**完了条件:** 「この受信箱を見れば必須メールが来る」状態になっている。

### Phase 1（2〜4日）— 広く取得・AI判定・タスク化

新規 GAS: `email_alert_ingestor.gs`（案）

| 処理 | 内容 |
|------|------|
| トリガー | **15分ごと**（クォータ余裕。定数 `EMAIL_POLL_MINUTES`） |
| 取得 | `is:unread -category:promotions -category:social -label:email-ingestor/done` |
| 上限 | 1 回あたり最大 N 通（例: 15）でクォータ・コスト保護 |
| 事前スキップ | ScriptProperties の denylist（From / ドメイン） |
| 判定 | Gemini に JSON で分類させる（サービス名も推定） |
| 作成 | 要対応のみ Notion へ |
| 通知 | Slack DM。メッセージに Message-ID を含め、👎 で学習できる形にする |
| 冪等 | `Message-ID` |

スクリプトプロパティ:

| キー | 用途 |
|------|------|
| `NOTION_TOKEN` | 既存 |
| `GEMINI_API_KEY` | 既存 |
| `SLACK_TOKEN` | 既存 |
| `EMAIL_MONITOR_ADDRESS` | 監視メール（必須。本体 or エイリアス） |
| `EMAIL_ALERTS_ENABLED` | kill switch |
| `EMAIL_DENYLIST_JSON` | 学習済み無視ルール（自動更新。人手編集は任意） |

実装: [`email_alert_ingestor.gs`](../email_alert_ingestor.gs) / 手順: [`mandatory-email-setup.md`](mandatory-email-setup.md)

**完了条件:** 未知のサービスメールでも、要対応なら Notion + Slack まで到達する（allowlist なし）。

### Phase 2（1〜2日）— ノイズ学習と運用品質

- Slack 👎 または Notion「対象外」→ denylist 自動追加  
- 同一案件の再送は既存タスクへコメント追記  
- 朝タスクに「メール由来・緊急」セクション  
- 週1で denylist の誤学習だけ見直す（allowlist メンテはしない）  

初期1〜2週間はノイズタスクが多少出る想定。  
そのたびに「無視」を教えると、以降の手作業は急減する。

### Phase 3（数日）— 「具体対応」の現実解（半自動）

「具体的な対応まで」は、最初は **実行ではなく手順の具体化** にする。

| 対応タイプ | Phase 3 の出力 | 実行者 |
|------------|----------------|--------|
| 請求情報の更新 | コンソール画面パス + 入力項目チェックリスト | 人 |
| セキュリティ通知の確認 | 確認すべき画面・ログのリスト | 人 |
| 証明書期限 | 更新手順と影響範囲メモ | 人 |
| リポジトリの依存脆弱性（Dependabot 等） | Notion タスク + 必要なら `AIステータス=AIに依頼` | Claude パイプライン |

### Phase 4（任意・慎重）— 限定自動実行

API で安全にできるものだけ。メール種別の登録テーブルは依然として作らない。

| 例 | 可否 |
|----|------|
| Notion / Slack 更新 | 可 |
| IAM 変更・課金手段変更・メール内リンク自動クリック | **不可** |

## 8. Gemini 判定プロンプト方針（概要）

入力: From / Subject / Body（先頭 N 文字） / 受信日時  

判定の中心質問（サービス名の一致より優先）:

> このメールを放置すると、課金停止・サービス停止・セキュリティ侵害・法的/契約上の期限切れなどの実害があり得るか？

出力（JSON 厳格）:

```json
{
  "category": "action_required | review | fyi | ignore | uncertain",
  "service": "AWS など（未知なら Other）",
  "urgency": "urgent | normal | low",
  "due_date": "2026-07-30 or null",
  "title": "50文字以内のタスク名",
  "summary": "2〜3文",
  "action_steps": ["...", "..."],
  "done_criteria": ["...", "..."],
  "phishing_risk": "low | medium | high",
  "confidence": 0.0,
  "ignore_reason": "ニュースレター等の場合のみ"
}
```

ルール例:

- allowlist は使わない（未知サービスでも `action_required` になり得る）  
- `phishing_risk=high` → `uncertain`、リンククリック手順は出さない  
- `confidence < 0.6` → `uncertain`（取りこぼしより過剰検知を許容。無視学習で収束させる）

## 9. セキュリティ・プライバシー

| リスク | 対策 |
|--------|------|
| フィッシングを正規と誤認 | リンク非推奨 + `phishing_risk`（allowlist 依存にしない） |
| 受信箱を広く読む | Promotions/Social 除外、処理上限、要約のみ Notion 保存 |
| API キー漏洩 | スクリプトプロパティのみ |
| 過剰通知 | 緊急即時 / 他はダイジェスト可。👎 で学習 |
| 無限ループ | 処理済ラベル + 既読化 + kill switch |

## 10. 成功指標（最初の 2 週間）
